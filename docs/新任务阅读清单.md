# Harbor 新任务阅读清单

这份清单用于每次创建一个新的 Harbor task。不要一开始把所有文件都研究完；按
任务所处阶段阅读即可。

## 一、创建前：先看任务规格

先看：

```text
docs/tasks/<task-name>-spec.md
```

只确认以下内容：

- Agent 最终需要提交什么文件；
- kernel 或程序的输入、输出和接口；
- 正确性检查什么；
- 是否测性能；
- reward 代表什么。

规格没确定时，不应该开始写 verifier。

## 二、Scaffold 后：按这个顺序看

### 1. `task.toml`

先确认任务身份和运行边界：

- `task.name` 是否正确；
- Agent 和 verifier timeout；
- 操作系统；
- 是否需要 GPU；
- 网络和环境声明。

此时不需要研究 Harbor 内部源码。

### 2. `instruction.md`

确认 Agent 实际能看到的题目：

- 输出路径；
- 文件格式；
- 函数或 kernel 接口；
- 允许和禁止的行为；
- 有没有泄露隐藏测试或标准答案。

### 3. `environment/Dockerfile`

确认 Agent 所处环境：

- 基础系统；
- 已安装的编译器和工具；
- Python、CUDA、`ptxas` 等依赖；
- 默认工作目录。

### 4. `solution/solve.sh`

确认 Oracle 如何完成任务：

- 最终写出什么文件；
- 输出路径是否和 instruction 一致；
- Oracle 是否只使用题目允许的接口。

### 5. `tests/test.sh`

确认 verifier 的入口：

- 它调用哪个 Python 或 Bash 检查程序；
- 失败时是否仍会产生合法 reward；
- 最终写 `reward.txt` 还是 `reward.json`。

### 6. `tests/*.py` 和其他测试文件

这是最需要仔细看的评分逻辑：

- 如何加载 Agent 输出；
- 测试用例和边界条件；
- 正确性判断；
- 性能计时；
- reward 计算；
- 异常和超时如何处理。

### 7. `README.md`

最后看任务摘要。README 用于帮助人快速定位，不应替代上面六类真实配置和代码。

## 三、Scaffold 阶段不要运行

刚 scaffold 出来的文件通常包含：

- 空的 `instruction.md`；
- 没有实现的 `solve.sh`；
- 只有 `pass` 的示例测试；
- 通用 Ubuntu Dockerfile。

此时运行得到 reward `1` 也没有意义，因为默认测试可能什么都没检查。

## 四、实现后：检查文件之间是否对齐

至少检查下面这条链路：

```text
instruction 声明的输出
        ↓
solve.sh 生成的输出
        ↓
test.sh 调用的 verifier
        ↓
verifier 读取同一个输出并写 reward
```

重点对齐：

| 内容 | 必须一致的位置 |
|---|---|
| 输出路径 | instruction、solve、tests |
| kernel 名称 | instruction、Oracle、verifier |
| 参数顺序和类型 | instruction、Oracle、verifier |
| GPU/系统要求 | task.toml、环境、运行命令 |
| timeout | task.toml、测试实际耗时 |
| reward 含义 | 规格、test.sh、verifier |

## 五、运行时：固定顺序

### 第一次：Oracle 正例

检查：

- 环境成功启动；
- `solve.sh` 被执行；
- verifier 被执行；
- reward 符合预期；
- `exception_info` 为空。

Oracle 不通过时，不运行真实 Agent。

### 第二次：人为负例

至少准备一个明确错误的输出，确认 verifier 返回 `0` 或预期的低分。只验证正例
不能证明测试真正有效。

### 第三次：真实 Agent

Oracle 和负例都正确后，才运行 Codex 或其他模型。

### 性能题额外检查

- 正确性失败时不能获得性能分；
- 计时不包含 JIT、内存分配和 Host/Device 拷贝；
- 保存原始时延，不只保存总 reward；
- Oracle 与 Candidate 使用相同 GPU 和启动配置；
- 多次运行的波动可解释。

## 六、运行后：按这个顺序看结果

```text
jobs/<job-name>/result.json
    ↓
jobs/<job-name>/<trial-name>/result.json
    ↓
verifier/reward.txt 或 reward.json
    ↓
verifier/test-stdout.txt
    ↓
agent/trajectory.json
    ↓
agent/sessions/.../rollout.jsonl
```

用途：

1. Job `result.json`：先看整体有几个 trial、平均 reward 和异常数；
2. Trial `result.json`：看单次 reward、各阶段耗时和异常；
3. verifier 输出：确认具体通过或失败原因；
4. `trajectory.json`：看 Agent 做了哪些关键操作；
5. `rollout.jsonl`：只有需要调查 Agent 原始行为时再看。

`config.json` 和 `lock.json` 主要用于复现配置，不是第一次阅读结果的重点。

## 七、每个新任务的最小验收清单

- [ ] 规格已经确定；
- [ ] scaffold 文件完整；
- [ ] `task.toml` 资源和 timeout 正确；
- [ ] instruction、Oracle、verifier 的接口一致；
- [ ] Oracle 正例得到预期 reward；
- [ ] 至少一个负例被正确拒绝；
- [ ] 真实 Agent 完成至少一次运行；
- [ ] 运行结果、版本、镜像和 GPU 信息可复现；
- [ ] 性能题保存原始计时数据和评分公式。

## 八、不需要每次重新看的内容

以下内容只在出现对应问题时再看：

- Harbor 框架源码：CLI 或生命周期行为不符合预期时；
- SIF 定义：需要新增或修改环境依赖时；
- Singularity GPU 补丁：并行分配或 GPU 可见性出问题时；
- Docker/WSL 配置：本地 Docker 连接失败时；
- 完整 Agent 原生 session：需要分析模型为什么成功或失败时。

需要理解整体生命周期时，回看
[`harbor-task-lifecycle.md`](harbor-task-lifecycle.md)；需要理解 jobs 输出时，回看
[`harbor-job-output.md`](harbor-job-output.md)。
